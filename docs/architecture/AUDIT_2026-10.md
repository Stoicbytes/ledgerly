# Architecture and data audit (October 2026)

A review of the whole repository: what the app is, how it is built, every call to Supabase,
failure states, and documentation. The aim was to fix what is wrong without rewriting what
works. Companion documents: [product definition](../PRODUCT.md),
[data access inventory](DATA_ACCESS.md), [database](DATABASE.md),
[edge cases](EDGE_CASES.md).

## Executive summary

The application is in good shape for a personal app. The structure is clear and consistent:
screens → stores → one data folder → Postgres functions under Row Level Security. Every rule is
checked in the database as well as in forms. There is no polling and no duplicate fetching, and
CI checks types, lint, format, tests, builds and bundle size. **No security hole was found**
(P0: none).

The real problems were in the gaps between "saved on screen" and "saved in the database", and
they could lose or double your entries:

## How the review was done

1. **Read the code paths end to end:** routes (`src/app`), the shell, every store, the sync
   orchestrator (`features/sync/cloudSync.ts`), the session provider, every repository in
   `src/lib/data`, the market and portfolio stores, the public site's server handler, and the
   migrations.
2. **Inventoried every Supabase call** with its trigger and frequency
   ([DATA_ACCESS.md](DATA_ACCESS.md)). All dashboard calls go through `src/lib/data` (enforced by
   lint), so the inventory is complete for the app code.
3. **Checked behaviour in the built web app** where code reading was not enough: dashboard
   screens stay mounted when you switch tabs (so the Portfolio editor loads once per session, not
   on every visit). That ruled out a suspected repeated query.
4. **Wrote a failing test for each defect, then fixed it** (except #4's display, verified through
   the store).

Baseline before changes: `main` at `0da5f77`; CI green; 468 dashboard tests, 33 portfolio tests;
web bundle 506.2 KiB.

## Supabase calls: result

- **Removed:** none. Nothing was unnecessary: no polling, no duplicate loads across screens (one
  store per kind of data, loaded once), no `select *` from browsers, no refetch after saves.
- **Added:** one targeted price reload (#4), only when a saved change adds a priced holding.
- **Made safer:** every database call now has a 30 s timeout (150 s for the price function), and a
  pending save is sent as soon as the tab is hidden.
- **Measured?** No. Counts come from the code and tests, not from a live project. To check:
  browser Network tab → filter `rpc/` → sign in, add an expense, add a fund.

## Architecture review

**What works well and should stay:**

- **One data door** (`src/lib/data`), Postgres functions instead of table access, `security
invoker` everywhere except three narrow public functions.
- **Load once, save differences** (ADR 0003): screens work on in-memory stores, sync is invisible
  and atomic, retries are safe because saves are upserts.
- **Domain logic is pure and tested** (`src/lib/domain`): money, FIFO, XIRR, budgets, validation.
- **Preview mode** makes the whole app usable without a backend, clearly labelled.
- **Decisions are recorded** (ADRs 0001–0011), and documents mostly matched the code.

**Weaknesses (not changed, with reasons):**

- `cloudSync.ts` keeps its state in module variables (`baseline`, `timer`, `inFlight`). It is
  small and well tested, so a class or library would add more than it removes. Keep, but keep it
  the only place that talks to `sync_ledger`.
- The Portfolio module saves per item instead of through the ledger batch. That is deliberate
  (ADR 0010: different data, different lifecycle) and should not be merged.
- The public site and dashboard now share an origin. Accepted (ADR 0011); the separation can be
  restored without code changes.

No large refactor was justified: components respect the 200-line limit (routes 80, enforced by
lint); `madge --circular` over the 426 source files found no circular imports (its 129 warnings
were not inspected); and every package in `dependencies` is either imported by the code or
required at runtime by Expo Router and React Native Web (`react-dom`, `@expo/metro-runtime`,
`react-native-screens`, `expo-constants`, `expo-system-ui`).

## Security review

- **Row Level Security** is forced on every user table, with the two-step (aal2) restrictive
  policy, owner-only foreign keys and audit by column name (DATABASE.md).
- **Keys:** only the publishable key reaches browsers; both apps refuse `sb_secret_` and
  service-role keys at start; the service role exists only in Edge Function secrets. CI fails if
  an `EXPO_PUBLIC_` variable is named like a secret.
- **Anonymous access:** only `portfolio_public`, `portfolio_preview` and `portfolio_contact`, each
  narrow (DATA_ACCESS.md, Q20–Q22).
- **Headers:** strict CSP per part, HSTS, frame blocking, `nosniff`; dashboard pages `noindex`.
- **Not verified here:** the live project's policies and settings (allowlist hook on, TOTP on,
  redirect URLs). The checklist is in `SUPABASE_SETUP.md` → "Verification before relying on it".

## Remaining issues and decisions for you

The three decisions were settled after the audit the way most finance apps do it (last save
wins with a reload on return; unbuilt screens hidden; receipts stored privately). See
[PRODUCT.md → Decisions](../PRODUCT.md#decisions-october-2026). An earlier version of this report
said receipt photos "stay on the device"; that was wrong: they were not kept anywhere and
disappeared on reload (#14).

- **Engineering, next:** route-level code splitting (#13), then incremental loading of history
  (#11).

## Developer handover (plain English)

- **What you have built:** a private web and phone app for your own money (expenses, accounts,
  budgets, splits, mutual funds, shares), notes, and a public portfolio site, all stored in your
  Supabase database and protected by sign-in with a two-step code.
- **How it works:** after sign-in the app loads all your data in one request and keeps it in
  memory. Each change you make appears instantly and is sent to the database about half a second
  later as one small batch. The database checks every rule again and only lets you see your own
  rows. Prices are fetched by a server function from AMFI and the exchanges, never by the browser.
- **Most important features:** fast expense entry, Stats and Budget, accounts and net worth,
  funds and shares with real returns (XIRR), tradebook import, and the portfolio editor.
- **How the frontend talks to Supabase:** only through `apps/command-center/src/lib/data`, by
  calling named Postgres functions (`load_ledger`, `sync_ledger`, `load_market`, the `portfolio_*`
  functions) with your sign-in token. No table is read directly from the browser.
- **Key architectural decisions:** one Expo codebase for web and phones (ADR 0001); the database
  as the security boundary (ADR 0002); load once, save differences in batches (ADR 0003); market
  data on the server (ADR 0004); money in paise (ADR 0005); the portfolio as a separate app served
  at the site's home page (ADRs 0010, 0011).
- **What to focus on next:** the import from your current app, then search and data export, then
  the PF/EPF tracker. Keep the core fast and reliable before adding modules.
